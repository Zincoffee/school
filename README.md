## 一、产品名称

**校园活动与机会平台** —— 面向在校学生、重点考虑新生使用体验的校园活动与机会信息站。

数据源为题目给定的 26 条校园活动（编号 01–26，见 `design/已知校园活动汇总.md`）。

## 二、解决的问题

| 问题 | 具体表现 | 本产品的应对 |
| --- | --- | --- |
| **信息散、难筛选** | 活动通知散落在群聊、公众号、海报里，学生要逐条翻找 | 26 条活动统一成卡片墙，可按门槛、状态、关键词筛选搜索 |
| **看不出"值不值得去"** | 新生不知道要不要门槛、在哪办、要不要报名、什么时候截止 | 每张卡片直接给出时间、地点、门槛、截止、报名方式；缺失项显式标注"未注明"，不让学生误以为"没有" |
| **组织者补不上信息** | 26 条中有 20 条未注明发布方，线下明确地点仅 4 条（15%）、收获信息 0 条 | 每个活动一个专属补充链接，组织者点开即可补齐并上传资料，无需注册 |
| **多来源信息的噪声** | 同一活动重复发布（09 是 01 的变更通知、20 是 03 的补充说明）、已过期的活动仍在传播、营销信息混入 | 变更通知合并为同一条活动的更新记录；过期条目默认不展示；营销条目标注风险 |

## 三、主要功能

- **活动卡片墙**：26 条活动无需分页；状态徽章（报名中／无需报名／长期／报名已截止／已结束／地点待定）；支持关键词搜索与门槛、状态筛选
- **活动详情**：要求、面向人群、地点、时间、报名截止、报名方式、名额、费用、收获；附该活动的更新记录
- **组织者补充信息**：凭专属链接补充或修正字段、填写变更原因、上传活动资料（PPT／Word／PDF／图片／txt／md）
- **附件在线预览**：图片与 PDF 直接渲染、txt 自动识别 GBK、md 渲染、docx／pptx 逐页提取文字；**全部在浏览器端完成，服务端不做任何转换**
- **变更留痕**：每次修改记录「字段／原值／新值／时间／原因／来源」，详情页可回溯
- **两种交付形态**：同一套逻辑，既能作为本地服务运行，也能打包成一个可直接转发的 HTML 文件

## 四、运行与使用说明

### 方式一：离线单文件版（最快，无需安装任何东西）

直接双击根目录的 **`校园活动与机会平台.html`**。26 条活动已内嵌在该文件中，不联网也能用，也可以直接发给别人（微信、邮件皆可），对方双击即可查看。

- 补充信息后点右上角**「导出 HTML」**，浏览器会下载一个包含改动的新文件，**用它替换旧文件**即可长期保存
- 该版本没有口令保护，任何拿到文件的人都能修改；改动也不会自动共享给他人

### 方式二：服务版（多人各自补充、汇总到同一份数据）

前提：已安装 Node.js 22 或更高版本（<https://nodejs.org>）。**不需要 Docker、不需要 `npm install`、不需要构建。**

双击 **`start.bat`**：检查 Node → 启动本地服务 → 2 秒后自动用 Edge 打开 `http://localhost:3000`。关闭窗口即停止服务。

### 常用命令

```bash
node server.js                          # 启动服务版（http://localhost:3000）
node server.js --reset                  # 清空 data/ 并由种子数据重新生成
node tools/build-standalone.js          # 重新生成离线单文件版
node tools/build-standalone.js --check  # 校验离线版是否为最新
node --test test/                       # 运行全部测试（94 项）
```

> 修改 `public/` 下的脚本或样式后需重新生成离线版；`test/standalone.test.js` 会检查这一点，过期时直接失败。

### 给活动组织者发补充链接

每个活动的补充口令保存在 `data/activities.json` 的 `editToken` 字段，链接形如：

```
http://localhost:3000/edit.html?id=01&token=<24 位口令>
```

把对应活动的链接发给该活动的组织者，对方点开即可补充，无需注册或登录。

## 五、自主设计的实用与创新内容

| 设计 | 做法与理由 |
| --- | --- |
| **补充口令机制** | 每个活动一个 96 bit 随机口令，组织者凭一条链接即可补充信息。**完全不需要注册、登录、账号体系与审核队列** —— 因为 26 条活动里有 20 条查不到发布方，做身份认证既无对象也无意义 |
| **去掉审核，保留留痕** | 不做"先审后发"流程（需要持续的人力），改为字段级变更记录：谁在什么时候把哪个字段从什么改成了什么、原因是什么，误改可追溯。**审核需要一个队列，留痕只需要一个数组** |
| **"未注明"显式呈现** | 缺失信息显示为"未注明"而不是留空。因为"未注明"≠"没有"：留空会让学生以为该活动没有收获，而"未注明"会促使他去问。这条规则同时也是给组织者的补充提示 |
| **自研 docx／pptx 文字提取** | docx／pptx 本质是 ZIP + XML，用浏览器与 Node 都内置的 `DecompressionStream('deflate-raw')` 自行解析中央目录、解压、抽取文字（`public/ooxml.js`）。**替代了原方案里需要预先下载的数百 KB 第三方库，保住了"零依赖、可离线"**，并让 pptx 也能预览（原方案只能提示"请上传 PDF"） |
| **生成式离线单文件版** | 领域逻辑抽成 `public/model.js` 供两种版本共用，再由 `tools/build-standalone.js` 把样式、脚本与数据**内联**成一个 HTML。因此不存在两份实现，也不会逐渐不一致；产物可复现（同样源码必然得到同样文件） |
| **离线版不依赖浏览器存储** | `file://` 下 localStorage／IndexedDB 各家行为不一致，因此不去赌它：改动同步回页内数据块，导出时用 `documentElement.outerHTML` 生成新的单文件，**用替换文件代替"保存"** |
| **变更通知合并** | 数据源里的 09、20 是 01、03 的补充通知而非新活动。产品不把它们当成两条信息展示，而是并入父活动的更新记录，并把 09 的地点回填给 01，同时过滤"不变"这类空操作记录 |
| **附件预览零服务端转换** | PDF 用 **Edge 内置阅读器**（省掉 PDF.js）、中文 txt 用 `TextDecoder` 自动识别 UTF-8／GBK、Markdown 先整体转义再套规则（内联 HTML 不生效、链接只放行 http／https）。因此服务端不需要 LibreOffice、Redis 与队列 |
| **零依赖、零构建** | 服务端只用 5 个 Node 内置模块，连 multipart 上传解析都用内置的 `Request.formData()`，没有手写解析器；无 `package.json`、无 `node_modules`、无构建步骤 |
| **安全上的三处关键设计** | ① 上传做扩展名 + 大小 + **magic number 文件头**三重校验，防改扩展名，并拒绝含宏格式；② 补充口令用 `timingSafeEqual` 比较，且**所有接口响应显式剔除口令字段**（有遍历式测试断言，防止任何人打开列表接口拿到全部口令）；③ 附件只存储与预览，服务端从不解析或执行上传内容 |
