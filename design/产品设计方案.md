## v3.0 修订说明

本版根据评审意见调整了产品主线：**从「发布驱动」改为「展示驱动 + 补充驱动」**。

| 变化 | v2.0 | v3.0 |
| --- | --- | --- |
| 内容来源 | 组织者先从活动库选定条目再发布，不发布则平台为空 | **26 条活动预置入库，上线即有内容**；组织者按卡片补充 |
| 主要动作 | 组织者「发布活动」 | 组织者「补充活动内容」（卡片右下角按钮） |
| 冷启动 | 需运营逐一邀约组织者 | 无需邀约，预置数据即可展示 |
| 原有机制 | — | 附件预览、要求地点标注、更新合并、时效状态机、信息完整度**全部保留** |
| 新增风险 | 白名单从源头消除虚假信息 | 补充入口重新引入信息注入风险 → 由第 5 章可信度分级治理 |

## 1. 需求解读

### 1.1 原始要求拆解

| 原文要求 | 本质问题 | 难度 |
| --- | --- | --- |
| 组织者发布活动信息，支持 PPT/Word/图片/txt/md | 富格式内容的**上传与在线浏览** | 中（格式转换是主要成本） |
| 在线浏览活动资料 | 让用户不下载就能看懂 | 中 |
| 帮助辨别活动是否值得参与 | **决策支持** | 高（产品设计难点） |
| 学生自主发布活动、招募伙伴 | 供给侧开放 | 中高 |
| 多来源信息可能产生的问题 | 真实性、重复、过期、营销噪声 | 高 |

### 1.2 三个用户角色

| 角色 | 核心诉求 | 关键痛点 | v3.0 中的主要入口 |
| --- | --- | --- | --- |
| **新生**（重点） | 这活动是什么、我能去吗、在哪、值不值得去 | 不知道门槛、找不到地点、怕白跑、怕被骗 | 卡片墙 + 详情页决策卡 |
| **活动组织者** | 让学生看懂自己的活动、招到人 | 平台已有自己的活动但信息不全，无法补充 | **卡片右下角「补充活动内容」** |
| 普通学生 | 快速找到对口机会 | 信息散落群聊/公众号，过期信息干扰 | 搜索筛选 + 新生专区 |

> v3.0 的关键认识：**卡片墙同时服务两类人**。学生看卡片判断"去不去"，组织者看卡片发现"我的活动信息不全，该补充了"。右下角按钮就是给后者的入口。

## 2. 产品定位与设计原则

> **一句话定位**：一个把校园活动摊开成卡片、让新生快速判断"值不值得去"、并让组织者随时把信息补全的校园机会平台。

**七条设计原则**

1. **展示优先**：平台先有内容，再谈运营。26 条预置数据即是最小可用产品。
2. **决策优先**：任何页面先回答"值不值得"，再展示"是什么"。
3. **补充不覆盖**：组织者补充的信息不静默覆盖平台原始数据，而是并列展示并记录变更。参见 09 号条目变更 01 号时间地点这一真实案例。
4. **来源永远可见**：每个字段都要能看出是「平台原始」「组织者确认」还是「学生补充·待核实」。
5. **"未注明" ≠ "没有"**：缺失显式显示为"未注明"，而非留空。缺失本身就是判断依据。
6. **过期即归档**：活动结束/报名截止后自动降级，默认从列表移除。
7. **新生默认友好**：首次进入不做空列表，给引导 + 现成的"新生友好"内容。

## 3. 数据基础分析

本节是对 `已知校园活动汇总.md` 的实际分析，所有机制都由此推导。

### 3.1 文件实际结构

文档为**三列表格**，共 26 条：

| 编号 | 信息 | 主要内容 |
| --- | --- | --- |
| 01 | “蓝桥杯”程序设计校内训练营 | 9月24日22:00报名截止；原计划9月20日起每周六19:00训练；面向全校学生；零基础可参加 |
| 09 | 程序设计训练营补充通知 | 因场地调整，首次训练改为9月21日19:30，地点改至实验楼A402；已报名同学无需重复提交；报名截止时间不变 |

**关键观察：表格没有独立的「要求」列和「地点」列。** 时间、截止、地点、面向人群、门槛、名额、费用全部混在「主要内容」这一整句散文里。因此"注明要求和地点"这件事，**前提是把散文拆成结构化字段**——已完成，见 `activities.seed.json`。

### 3.2 字段覆盖率（26 条实测）

下表数字**由 `activities.seed.json` 直接统计**（分母 26），与该数据文件 `_meta.coverage` 完全一致：

| 字段 | 有效条数 | 覆盖率 |
| --- | --- | --- |
| 具体时间 | 16 | 62% |
| 参与门槛/要求（含非硬性偏好） | 15 | 58% |
| 投入要求 | 15 | 58% |
| 面向人群/资格限制 | 12 | 46% |
| 报名截止（有具体日期） | 8 | 31% |
| **线下明确地点** | **4** | **15%** |
| 名额限制 | 5 | 19% |
| 费用（提及，但均无金额） | 2 | 8% |
| **收获（学分/工时/证书）** | **0** | **0%** |

**地点字段的完整分布**：

| 地点状态 | 条数 | 条目 |
| --- | --- | --- |
| 明确（线下） | 4 | 02、09、10、21 |
| 线上（无需地点） | 2 | 04、17 |
| 待确认 | 2 | 22、23 |
| **未注明** | **18** | 其余全部 |

**三个必须写进方案结论的发现：**

1. **地点只有 15% 覆盖率。** 这与 v3.0 的补充机制直接相关：**18 条缺失地点的活动，正是最需要组织者补充的对象**。补充机制不是附加功能，而是填补数据缺口的主路径。
2. **收获字段 0 条**：没有任何一条提到学分、工时或证书。决策卡的"收获"行将长期显示"未收录"。**产品不能编造，也不应留空**。
3. **费用字段只统计到 2 条，且两条都没有金额**（12 为"未提供"、22 为"AA"）。"已知具体费用金额"实为 **0 条**。

### 3.3 六类信息陷阱与处理策略

| 陷阱类型 | 数据实例 | 产品处理 |
| --- | --- | --- |
| **同一活动重复/增量发布** | 01 ↔ 09（训练营场地与首次时间变更）、03 ↔ 20（开发名额已满，改补设计/材料） | 活动库以「活动」为单位；补充通知**不独立成卡**，合并为父活动的**变更记录** |
| **时效已过** | 04（直播 9/18 已结束，回放待上传）、19（报名 9/18 已截止，仅可候补）、17（网盘链接 9/22 失效） | 状态机自动标注；列表默认过滤；"待回放"作为独立状态 |
| **信息不完整** | 12（费用未提供）、16（截止未注明）、22/23（地点未定）、24/25（无主办方无地点） | 卡片显示**信息完整度**并逐项标"未注明"；**这是补充按钮的主要触发场景** |
| **疑似营销/风险** | 24（"零门槛、日结"，要求加私人微信，无主办方）、25（标题为技术交流，正文是商家购买链接） | 风险标记；高风险条目不予收录或强制警示；**补充内容同样经过此规则**（见 5.4） |
| **无需报名 / 非先到先得** | 02、04、10、15、21、26（无需报名）；14（报名表≠录取）；07（意向登记≠最终提交） | 报名方式支持"无需报名·直接到场"；"需审核"必须显式提示 |
| **非活动类信息** | 17（Python 资料合集，长期开放） | 增加"资料/机会"类型，不套用"活动时间/地点/报名"字段 |

### 3.4 由此确定的产品约束

1. 26 条活动**预置入库并直接展示**——这是 v3.0 的起点，不等待任何人发布。
2. 卡片必须承载判断要素（时间、地点、门槛、截止、状态、完整度），不止是标题。
3. 补充入口挂在**每张卡片**上，且必须记录**谁在什么时候补了什么**。
4. 平台原始数据与补充数据**分区展示**，任何与原值不同的补充都进入变更记录，不得静默覆盖。
5. 必须支持**六种时效状态**：报名中 / 报名已截止（可候补）/ 已结束（含待回放）/ 长期有效 / 地点待定 / 链接可能失效。
6. 必须支持**非活动类**（资料）类型。

## 4. 核心机制一：活动卡片墙

### 4.1 卡片信息设计

26 条数据量小，**不需要分页**，一屏可滚完。卡片必须让新生在不点击的情况下完成初筛：

```
┌──────────────────────────────────────────────────┐
│ 01  “蓝桥杯”程序设计校内训练营                     │
│                          [报名中] 完整度 ●●○○○    │
├──────────────────────────────────────────────────┤
│ 时间   每周六 19:00（9月20日起）                   │
│ 地点   未注明 ← 待补充                            │
│ 门槛   零基础可参加 · 面向全校学生                 │
│ 截止   9月24日 22:00                              │
│ ⚠ 时间与地点有变更，见补充说明                     │
│                                                   │
│                        [我是组织者 · 补充信息]     │
└──────────────────────────────────────────────────┘
```

**设计要点**

- **状态徽章**放右上角：报名中 / 报名已截止 / 已结束 / 长期 / 地点待定 / 已下架。
- **信息完整度**用进度点表示（5 项关键信息：时间、地点、报名截止、名额、费用），并直接列出缺失项。"未注明"不隐藏——它同时是给学生的风险提示和给组织者的补充提示。
- **整卡可点击**进入详情；右下角按钮必须**阻止事件冒泡**，避免点按钮时跳转详情。
- 已结束与报名已截止的卡片默认不展示（可通过筛选调出）。

### 4.2 筛选与检索

- 筛选：时间（今天/本周/本周末）、类型、门槛（零基础/需基础）、面向人群、报名状态、**信息完整度**、校区。
- 排序：综合（截止紧迫度 + 完整度 + 新鲜度）、最新补充、即将截止。
- 检索：标题 + 要求 + 地点 + 补充内容 + 附件抽取文本。
- **收藏/报名过的活动**在卡片上有标记，便于回访。

### 4.3 这一机制解决了什么

v2.0 的最大风险是"冷启动无内容，新生看到空列表即流失"，因此需要运营逐一邀约组织者。v3.0 用预置数据把这个风险直接消除了：**平台第一次部署就有 26 条可看、可筛、可判断的活动**。这使 P0 的开发量明显小于 v2.0。

## 5. 核心机制二：组织者补充内容

这是本次改动的核心，也是 v3.0 最大的风险点，因此设计得比其他部分更细。

### 5.1 补充入口

每张卡片**右下角**一个按钮，点击后在当前页打开补充表单（抽屉/模态，不跳页，避免丢失浏览上下文）：

```
补充活动内容 · 01 “蓝桥杯”程序设计校内训练营

① 你的身份
   ○ 我是该活动的组织者/成员      ○ 我是知情学生      ○ 其他
② 补充信息（只填你能确认的，留空表示不确定）
   地点      [实验楼 A402                    ]
   名额      [                              ]
   费用      [                              ]
   收获      [ ] 学分 [ ] 志愿工时 [ ] 证书 [ ] 技能
   报名方式  [下拉：无需报名/站内/外链/群组/需审核]
   变更说明  [首次训练改为9月21日19:30         ]
③ 补充说明（自由文本）  [                          ]
④ 上传活动资料          [PPT / Word / 图片 / txt / md]
⑤                [提交]  （组织者直发；学生补充需核实）
```

### 5.2 四层可信度分级（本机制的关键）

**问题**：按钮写的是"活动组织者补充"，但 26 条数据里有 **20 条未注明发布方**（只有 21 号计算机学院、26 号外国语学院有明确发布方）。也就是说，"组织者"这个身份在多数条目上**无法直接验证**。

因此不能只做一种补充，必须按补充人身份分级：

| 补充人身份 | 如何验证 | 生效策略 | 展示标识 |
| --- | --- | --- | --- |
| 组织者（已认领该活动） | 认领审核通过 / 官方域名邮箱匹配（如 @计算机学院） | **直接生效** | 组织者已确认 ✓ |
| 组织者（首次补充，未认领） | 校园邮箱/学号 + 人工审核 | 审核通过后生效 | 组织者已确认 ✓ |
| 在校学生（信息知情人） | 校园邮箱/学号认证 | **不覆盖平台字段**，作为并列信息展示 | 学生补充 · 待核实 |
| 平台运营 | 后台账号 | 直接生效 | 平台录入 |

**"认领"机制**：组织者首次补充时，若该活动发布方明确（如 21 号计算机学院），要求用**对应身份**验证；若发布方未注明（20 条），则进入人工审核，审核通过后该账号成为该活动的组织者，后续补充可直发。

**为什么必须分级**：如果只允许组织者补充，那 20 条无法验证发布方的活动将**永远补不上信息**，地点覆盖率会停在 15%——而这恰恰是补充机制要解决的问题。如果允许所有人补充且直接生效，则虚假信息可以瞬间注入，v2.0 用白名单建立的信任基础会在一次改动中全部丧失。分级是这两难之间唯一可行的解。

### 5.3 补充不覆盖：字段级来源与变更记录

**核心规则：任何与原值不同的补充，都不静默覆盖，而是并列展示并留痕。**

以 01 号活动为例（这正是数据源里 09 号条目的真实情况）：

```
┌ 📌 要求与地点 ── 来源：平台活动库（可信基准）────┐
│ 要求   面向全校学生 · 零基础可参加                │
│        需在 9月24日 22:00 前报名                  │
│ 地点   实验楼 A402                                │
│        组织者已确认 · 9月19日更新                 │
│        原值：未注明                               │
│        ⚠ 变更：首次训练改为 9月21日 19:30          │
│ 未注明  名额 · 费用 · 收获                        │
│ 完整度  ●●○○○  2/5                              │
└──────────────────────────────────────────────────┘
```

- 每个字段带**来源标签**（平台原始 / 组织者确认 / 学生补充）与**更新时间**。
- 与原值不同时，同时显示**原值**，并进入该活动的**变更记录**（时间线，可展开）。
- 学生补充始终以独立区块展示，标注"未经组织者确认"，**不并入**平台字段区。

### 5.4 防滥用（必须有，否则一次改动就毁掉产品）

| 风险 | 措施 |
| --- | --- |
| 未登录用户注入信息 | 必须登录并完成校园邮箱/学号认证才能补充 |
| 单人刷屏 | 单账号对单活动同时只允许 1 条待审补充；提交限速 |
| 营销/诈骗内容 | 复用 24、25 号条目的反例规则：命中"加私人微信""日结""购买链接""零门槛"等关键词即转人工审核（见 3.3） |
| 恶意覆盖时间地点 | 补充不覆盖原值（5.3）；误导性补充可被举报 |
| 附件投毒 | 附件走第 8 章的安全约束：白名单 + magic number 校验、拒宏格式、ClamAV 扫描、转换隔离 |
| 无法追责 | 所有补充与审核操作写入审计日志，保留补充人、时间、前后值 |

**处置动作**分四级：驳回补充 → 下架该补充 → 限制补充权限 → 封禁账号。

### 5.5 一个必须你确认的界面问题

**卡片右下角按钮的位置我按你的要求实现了，但它在受众上有个错位**：卡片的读者主要是**学生**，而按钮服务的是**组织者**。学生看到"我是组织者 · 补充信息"会想"我又不是组织者"，反而干扰主要任务（判断去不去）。

三种处理方式，建议第一种：

| 方案 | 表现 | 取舍 |
| --- | --- | --- |
| **A. 身份感知（建议）** | 未登录/学生：显示弱化的文字链"我是组织者？补充信息"；已认领组织者：显示实心主按钮"补充活动内容" | 两类用户各得其所，但需判断登录身份，实现略复杂 |
| B. 统一弱化 | 所有访客都显示描边次要按钮的同一文案 | 实现最简单，但组织者不易发现入口 |
| C. 统一主按钮 | 按原文照做，所有访客都显示实心按钮 | 最抢眼，但会抢走「查看详情」的注意力，学生易困惑 |

详见第 18 章问题 4。

## 6. 核心机制三：要求与地点标注（与补充信息合流）

标注块位于**活动资料下方**，是"帮助学生判断"的主要载体。v3.0 的变化是：**补充信息也汇入这里**，但按来源分区。

```
┌ 📎 活动资料（发布者提供，平台未逐份核验）────────┐
│  招新宣讲.pptx    24 页   [在线预览] [下载]       │
│  报名须知.docx     2 页   [在线预览] [下载]       │
│  场地示意.png              [查看大图]             │
└──────────────────────────────────────────────────┘

┌ 📌 要求与地点 ── 平台活动库 + 组织者确认 ────────┐
│  要求   面向全校学生 · 零基础可参加                │
│         每周六 19:00 训练，需持续参与              │
│         需在 9月24日 22:00 前报名                  │
│  地点   实验楼 A402  组织者已确认 · 9月19日        │
│         [地图导航 · 步行 8 分钟]                   │
│  未注明  名额 · 费用 · 收获                        │
└──────────────────────────────────────────────────┘

┌ 💬 学生补充（未经组织者确认）────────────────────┐
│  昵称·计算机学院·大二  9月19日                     │
│  "上次是在实验楼A402，从东门进去右转"              │
│  [有帮助 3]  [存疑 0]                              │
└──────────────────────────────────────────────────┘
```

三个设计要点：

1. **来源分区是可信度的基础**：平台/组织者确认为一块，学生补充为另一块，视觉上不混淆。
2. **"未注明"行不能省**：学生看到"收获未注明"会去问，看到空白会以为没有。
3. **页首决策卡仍要有摘要**：标注在文件下方需要滚动，因此"要求/地点/截止"三项关键结论同时出现在页首决策卡中。

## 7. 核心机制四：更新合并与时效管理

### 7.1 更新合并

活动库为两层结构：**活动（父）** + **变更记录（子）**。v3.0 中变更记录有三个来源：数据源中的补充通知、组织者补充、平台运营修正。

| 父活动 | 变更来源 | 变更内容 |
| --- | --- | --- |
| 01 蓝桥杯训练营 | 09 补充通知 | 首次训练：9/20 → **9/21 19:30**；地点：未注明 → **实验楼 A402** |
| 01 蓝桥杯训练营 | 组织者补充 | （后续由组织者产生） |
| 03 创新创业团队招募 | 20 补充说明 | 招募方向：开发/设计/材料 → **开发已满，仅补设计/材料** |

卡片上显示 `⚠ 时间与地点有变更`，详情页展开时间线对比。

### 7.2 时效状态机

```
报名中 ──截止时间过──> 报名已截止 ──可候补──> 候补中
   │
   └──活动结束──> 已结束 ──有回放──> 已结束（回放可看）

长期有效（无截止）──> 长期展示，不自动过期
地点待定 ──地点确认──> 报名中
```

| 状态 | 数据实例 | 卡片表现 | 详情页表现 |
| --- | --- | --- | --- |
| 报名中 | 01、03、05 | 正常展示 | 报名按钮可用 |
| 报名已截止（可候补） | 19 | 默认过滤 | 灰条"报名已于 9/18 截止，现场有余位可候补" |
| 已结束 · 待回放 | 04 | 默认过滤 | 灰条"直播已结束，预计 9/20 上传回放"，提供订阅 |
| 长期有效 | 08、16 | 正常（标注"长期"） | 无倒计时 |
| 链接可能失效 | 17 | 正常 | 警示"网盘提取信息有效至 9/22" |
| 地点待定 | 22、23 | 正常但降权 | 显示"待确认"，可订阅地点确认通知 |

## 8. 附件在线浏览

需求明确要求支持 PPT、Word、图片、txt、md。**不能要求用户下载 30 页 PPT 才能判断**，因此设计转换流水线：

| 格式 | 预览方案 | 兜底 |
| --- | --- | --- |
| `.pptx` / `.ppt` | LibreOffice 无头转 PDF → PDF.js 逐页渲染；先生成前 5 页给首屏，其余按需转 | 转换失败提供原件下载 |
| `.docx` / `.doc` | 转 PDF 渲染（版式保真） | 同上 |
| `.png` / `.jpg` / `.webp` / `.gif` | 直接渲染 + 多尺寸缩略图 | — |
| `.txt` | **编码探测**（UTF-8 / GBK）后纯文本渲染 | 探测失败按 UTF-8 强解 |
| `.md` | markdown-it 渲染 + 代码高亮 + 外链图片代理 | — |

**流水线**：上传 → 原件存对象存储 → 入队 → 转换 Worker → 产物入库 → 状态回写。
状态机：`pending → processing → ready / failed`，前端显示"正在生成预览"，不阻塞补充提交。

**两个易踩的坑**：
- 中文 txt 大量为 GBK，按 UTF-8 读会乱码，**必须做编码探测**。
- 转换是 CPU 密集型且要跑他人文档，**必须独立容器、禁外网、限时限额**。

**安全约束（P0 即需落地）**：扩展名白名单 + magic number 双校验、拒绝宏格式（`.docm`/`.pptm`/`.xlsm`）、单文件 ≤50MB、单活动 ≤10 个附件、ClamAV 扫描。

```
⚡ 一页看懂
```

## 11. 新生引导

- **首次进入三步引导**：选院系与年级 → 选 3 个兴趣标签 → 生成个性化排序（不做空列表，26 条卡片始终可见）。
- **新生专区**：聚合"零门槛 + 无需组队 + 无需报名 + 时间短"的活动，如 02、10、21。

- **校园节奏提示**：开学季/期中/期末常见机会类型的轻量提示。

## 12. 管理后台

v3.0 的后台以**补充内容审核**为重心：

| 模块 | 功能 |
| --- | --- |
| **补充审核队列** | 学生补充、组织者首次补充、高风险关键词命中，批量通过/驳回 + 理由模板 |
| **认领审核** | 组织者身份核验，通过后授予该活动的直发权限 |

| 风险处置 | 24、25 类条目及违规补充的下架/警示/限流，处置留痕 |
| 数据看板 | 字段覆盖率、完整度分布、补充量与通过率、举报与处置时效 |

**运营重点指标**：地点覆盖率（当前 15%）、收获覆盖率（当前 0%）、**组织者认领数**——前两个数字的改善直接等于产品质量的改善，第三个决定补充机制能否跑起来。

### 13.1 页面清单

### 13.2 数据模型

| 实体 | 关键字段 |
| --- | --- |
| `Activity` | 编号、名称、别名[]、原始描述、**字段值均带来源**（platform / organizer / student）、publisher_type、risk_level、status、info_completeness、missing_fields[] |
| `FieldValue` | 活动、字段名、值、**来源**（平台原始/组织者确认/学生补充）、更新人、更新时间、原值 |
| `Supplement` | 活动、补充人、申报身份、认证级别、字段变更 JSON、自由文本、附件[]、状态（待审/生效/驳回）、审核人、时间 |
| `ActivityUpdate` | 活动、变更来源（数据源通知/补充/运营）、字段、变更前、变更后、生效时间 |
| `Claim` | 活动、申请人、身份凭证、审核状态、审核人 |
| `Attachment` | 活动、补充记录、原文件名、mime、大小、存储 key、转换状态、产物 key、页数、抽取文本 |
| `User` | 昵称、院系、年级、认证状态、角色 |
| `Registration` | 活动、用户、状态、来源、签到码 |
| `Report` | 目标（活动/补充）、理由、举报人、处置状态 |
| `AuditLog` | 操作人、动作、目标、前后状态、时间 |

**关键设计**：字段级来源（`FieldValue.source`）是本方案的核心数据结构——没有它就无法实现 5.3 的"补充不覆盖"与"来源永远可见"。

```
Activity 1 ──── n FieldValue        （每个字段一份来源与历史）
    1
    ├──── n Supplement ──── n Attachment
    ├──── n ActivityUpdate
    ├──── n Claim
    ├──── n Registration
    └──── n Report
```

## 15. 技术选型与路线图

### 15.1 技术选型

| 层 | 建议 | 理由 |
| --- | --- | --- |
| 前端 | Next.js + TypeScript + Tailwind | SSR 让详情页可分享（学生常从微信打开链接） |
| 后端 | NestJS（或 MVP 用 Next.js API Routes） | 补充审核与权限逻辑会快速变复杂 |
| 数据库 | PostgreSQL + Prisma | 字段级来源需要清晰的关系模型；`pg_trgm` 支撑中文模糊检索 |
| 对象存储 | S3 兼容（本地 MinIO） | 原件与转换产物都需存储并可签名访问 |
| 队列 | Redis + BullMQ | 转换必须异步，否则上传接口超时 |
| 转换服务 | 独立容器 + LibreOffice 无头 + ClamAV | 隔离不可信文档，禁外网，限时限额 |
| 预览 | PDF.js / react-pdf | 免商业授权，逐页渲染对大 PPT 友好 |
| 部署 | Docker Compose（校内服务器） | 数据不出校、成本可控 |

### 15.2 路线图

| 阶段 | 范围 | 目标 |
| --- | --- | --- |
| **P0**（1–2 周） | 26 条预置入库 → **活动卡片墙**（筛选/搜索/状态徽章/完整度）→ 详情页（含要求与地点标注）→ **补充表单**（结构化字段 + 附件上传 + 在线预览）→ 简版审核后台 | 跑通"看卡片 → 补信息 → 学生看懂"主闭环 |
| **P1**（2 周） | 四层可信度分级与认领、字段级来源与变更记录、学生补充分区展示、举报与处置、报名（含无需报名/需审核/候补/外链）、时效状态机与自动归档 | 让补充信息可信、可追溯 |
| **P2** | 组队找搭子、新生引导与专区、`.ics` 课表冲突检测、签到、消息通知、申请新增活动 | 提升参与率与留存 |

## 16. 非功能需求、指标与风险

### 16.1 非功能需求

**安全**：上传白名单 + magic number 校验、拒宏格式、ClamAV、转换隔离；RBAC + 资源级所有权校验；附件走签名临时 URL；补充操作全量审计。
**性能**：卡片墙首屏 < 1.5s（26 条无需分页）；详情首屏 < 1.5s；预览首屏 < 1.5s（大文件先出前几页）。
**隐私**：学号仅后台可见；补充人默认展示昵称+院系+年级；联系方式不公开，仅站内私信；提供注销与数据导出。

### 16.2 指标体系

| 类别 | 指标 |
| --- | --- |
| 北极星 | 每周有效参与数（站内报名或外链点击后 7 天内确认参与） |
| **补充机制健康度（本版新增）** | **地点覆盖率**（当前 15%）、**收获覆盖率**（当前 0%）、**组织者认领数**、补充提交量、补充通过率、平均审核时长 |
| 学生体验 | 卡片点击率、详情页停留、首周报名转化率、新生专区点击率 |
| 治理 | 过期活动归档及时率、重复条目合并率、举报率、违规补充处置时效 |
| 功能健康度 | 附件预览成功率与首屏耗时、转换失败率 |

### 16.3 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **补充入口被滥用**（本版最大风险） | 虚假信息注入，信任基础崩塌 | 四层可信度分级（5.2）+ 补充不覆盖（5.3）+ 关键词风控 + 审计留痕（5.4） |
| **20 条活动无明确发布方，补不上信息** | 地点覆盖率停在 15%，补充机制空转 | 认领审核 + 开放学生补充作为并列信息（5.2）；运营主动邀约已知发布方（21、26） |
| **"组织者"身份难验证** | 无法判断补充是否可信 | 已认领身份走直发；未认领走人工审核；学生补充永久标注"待核实" |
| 卡片右下角按钮造成受众错位 | 学生困惑，主任务受干扰 | 身份感知展示（5.5 方案 A） |
| 学生补充质量低 | 噪声增加 | 补充分区展示 + "有帮助/存疑"反馈 + 低质补充折叠 |
| 收获信息全缺 | 决策卡无法回答"值不值得" | 显式标注"未收录" + 开放组织者补充；不编造 |
| 转换服务资源开销 | 上传卡顿、成本高 | 异步队列 + 限流 + 大文件只转前几页 |

## 18. 待决策问题

1. **补充信息是"先审后发"还是"先发后审"？** 学生补充我建议先审；组织者（已认领）建议直发 + 抽检。这直接取决于审核人力。
2. **"组织者"身份如何认定？** 20 条活动未注明发布方。认领需要什么凭证（院系邮箱域名？社团负责人确认？指导单位盖章？）
3. **是否允许普通学生补充？** 若只允许组织者补充，未注明发布方的活动可能长期无信息；若开放学生补充，则需要 5.2 的分区展示与"有帮助/存疑"机制。**这是补充机制能否补上 18 条缺失地点的关键。**
4. **卡片右下角按钮如何呈现？** 按受众错位的分析（5.5），建议采用身份感知方案 A；若希望实现最简单，选方案 B。**这条需要你确认。**
5. **是否需要"申请新增活动"入口？** 若不需要，平台将永久固定为这 26 条，原需求中"学生自主发布活动"只能通过已有的 22、23 体现。
6. **是否需要立即落地代码？** 若需要，建议 P0 顺序为：卡片墙 → 详情页 → 补充表单 → 附件转换流水线（技术风险最高，建议并行先做技术验证）。
