| 项目 | 内容 |

## 1. 目标与约束

### 1.1 技术目标

| 目标 | 具体要求 |
| --- | --- |
| 极简部署 | 双击 `start.bat` 即可运行并在 Edge 打开；不装 Docker、不跑 `npm install`、无构建 |
| 零依赖 | 只使用 Node 内置模块；不引入任何第三方运行时依赖 |
| 数据量匹配 | 26 条活动、单机单人使用；不需要数据库、队列、对象存储、缓存 |
| 可维护 | 服务端单文件、前端无框架，改动后刷新即生效 |
| 可验证 | 有可重复运行的自动化测试（`node --test`，同为内置，零依赖） |

### 1.2 明确排除的技术

PostgreSQL / Prisma、Redis / BullMQ、MinIO / S3、LibreOffice 服务端转换、ClamAV、PDF.js、Docker、Webpack / Vite / Next.js、任何 npm 运行时依赖。

排除理由均为**规模不匹配**：26 条数据的读写用 JSON 文件即可；文档转换移到浏览器端后，队列与转换服务失去存在意义。

### 1.3 已在本机实测的内置能力

本方案的关键设计都建立在下列**实测结论**上，而非文档推断（环境：Node v24.19.0，Windows 11）：

| 能力 | 用途 | 实测结果 |
| --- | --- | --- |
| `Request` + `formData()` | **解析 multipart 上传**（零依赖，无需手写解析器） | ✅ 含二进制文件、中文表单值、中文文件名均正确 |
| `TextDecoder('gbk')` | 中文 txt 预览 | ✅ 正确解码 GBK 字节 |
| `TextDecoder('utf-8', {fatal:true})` | 编码探测 | ✅ 遇到 GBK 字节抛错，可据此回退 |
| `node:test` | 自动化测试 | ✅ `require('node:test')` 可用 |
| `crypto.randomBytes` / `timingSafeEqual` | 口令生成与校验 | ✅ 可用 |
| `fs.promises.rename` | 原子写入 | ✅ 可用 |
| `node:sqlite` | 升级路径 | ✅ 无需 flag 即可用（MVP 不使用） |

> 其中第一项最关键：`Request.formData()` 让 multipart 解析不必手写，**删掉了本方案里最容易出错的一块代码**。

## 4. 数据层设计

### 4.1 数据文件与职责分离

| 文件 | 角色 | 谁写 |
| --- | --- | --- |
| `design/activities.seed.json` | **只读导入源**，来自数据源文档的拆解结果 | 人工维护（不改） |
| `data/activities.json` | 运行时数据，被补充编辑修改 | `server.js` |
| `data/history.json` | 字段级变更记录，只追加不修改 | `server.js` |

分离的好处：随时可用种子数据重新初始化（删除 `data/` 即回到初始状态），且原始导入数据不被运行时修改污染。

### 4.2 首次启动初始化（bootstrap）

```
server.js 启动
  └─ data/activities.json 不存在？
       ├─ 是 → 读取 design/activities.seed.json，为每条活动生成 24 位十六进制补充口令，
       │        写入 data/activities.json；同时创建空 history.json 与 uploads/
       └─ 否 → 直接加载
```

口令生成：`crypto.randomBytes(12).toString('hex')` → 24 位十六进制（本机实测可用）。

### 4.5 原子写入与写串行化

单进程仍可能同时处理多个请求（如批量上传），因此：

1. **原子写**：先写 `xxx.json.tmp`，再 `fs.promises.rename` 覆盖目标文件（同分区 rename 为原子操作）。
2. **写串行化**：模块内维护一个 `Promise` 队列，所有写操作 `await` 前一个完成，避免读-改-写竞争。

```js
let writeChain = Promise.resolve();
function enqueueWrite(task) {
  writeChain = writeChain.then(task, task);   // 前一个失败也不阻断后续
  return writeChain;
}
async function atomicWriteJson(file, obj) {
  const tmp = file + '.tmp';
  await fs.writeFile(tmp, JSON.stringify(obj, null, 2), 'utf8');
  await fs.rename(tmp, file);
}
```

### 4.6 补充口令

| 项目 | 设计 |
| --- | --- |
| 生成 | `crypto.randomBytes(12).toString('hex')`，24 位十六进制（96 bit 熵） |
| 存储 | `data/activities.json` 中每条活动的 `editToken` |
| 校验 | `crypto.timingSafeEqual` 比较等长 Buffer，避免时序侧信道 |
| 传送 | 编辑页 URL：`/edit.html?id=01&token=<token>` |
| 重置 | 手动删除该活动的 `editToken` 后重启服务（bootstrap 逻辑只补缺失的口令） |
| 边界 | 口令即凭证，无账号体系。仅适用于本地/内网运行，**不可直接暴露公网**（见第 12 章） |

## 5. 服务端设计

### 5.1 路由表

| 方法 | 路径 | 作用 | 需要口令 |
| --- | --- | --- | --- |
| `GET` | `/`、`/index.html` | 卡片墙 | 否 |
| `GET` | `/activity.html`、`/edit.html`、`/app.js`、`/style.css`、`/vendor/*` | 静态资源 | 否 |
| `GET` | `/api/activities` | 卡片墙数据（支持筛选参数） | 否 |
| `GET` | `/api/activities/:id` | 详情 + 附件列表 + 变更记录 | 否 |
| `GET` | `/api/activities/:id/verify` | 校验口令是否有效 | 是（query） |
| `PUT` | `/api/activities/:id` | 保存补充/修正 | 是（query） |
| `POST` | `/api/activities/:id/files` | 上传附件 | 是（query） |
| `GET` | `/files/:id/:name` | 读取附件 | 否 |

接口总数 6 个（不含静态资源）。**响应统一为 JSON**，出错时返回 `{ "error": "<code>", "message": "<中文说明>" }`。

### 5.2 请求处理骨架

```js
const server = http.createServer(async (req, res) => {
  try {
    const url = new URL(req.url, 'http://localhost');
    if (url.pathname.startsWith('/api/')) return await handleApi(req, res, url);
    if (url.pathname.startsWith('/files/')) return await serveUpload(req, res, url);
    return await serveStatic(req, res, url);
  } catch (err) {
    res.writeHead(500, { 'content-type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({ error: 'internal', message: String(err.message) }));
  }
});
server.listen(3000, '127.0.0.1');   // 只绑定回环地址
```

**关键**：`server.listen(3000, '127.0.0.1')` 只绑定回环地址，天然不对外网暴露。这是第 12 章安全边界的基础。

### 5.3 静态文件服务与路径穿越防护

```js
const PUBLIC_DIR = path.join(__dirname, 'public');
async function serveStatic(req, res, url) {
  const rel = url.pathname === '/' ? 'index.html' : url.pathname.slice(1);
  const target = path.resolve(PUBLIC_DIR, rel);
  // 必须仍在 public/ 之内，阻断 ..%2f 之类的穿越
  if (!target.startsWith(PUBLIC_DIR + path.sep)) return notFound(res);
  ...
}
```

MIME 类型只需覆盖 `.html .js .css .png .jpg .svg .ico`（各类附件由 `/files/` 路由处理，统一按存储时的类型返回）。

### 5.4 补充口令校验

```js
function tokenOk(activity, supplied) {
  if (!activity.editToken || typeof supplied !== 'string') return false;
  const a = Buffer.from(activity.editToken, 'utf8');
  const b = Buffer.from(supplied, 'utf8');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

注意：返回给浏览器的活动对象**必须剔除 `editToken`**——否则任何人打开卡片墙接口就能拿到全部口令。这是本方案最需要小心的一处：

```js
function publicView(activity) {
  const { editToken, ...rest } = activity;   // 显式剔除
  return rest;
}
```

### 5.5 文件上传处理

利用 Node 内置的 `Request` + `formData()`，无需手写 multipart 解析（已实测）：

```js
async function readForm(req) {
  const r = new Request('http://localhost' + req.url, {
    method: req.method,
    headers: req.headers,
    body: req,              // IncomingMessage 本身就是 Readable 流
    duplex: 'half'          // 流式 body 必需
  });
  return r.formData();
}
```

处理流程：

```
1. 校验口令 → 失败 403
2. 读取 formData
3. 逐个文件校验：扩展名白名单 → 大小上限 → magic number
4. 校验活动当前附件数 < 10
5. 文件名安全化（去掉路径分隔符、控制字符；重名时追加序号）
6. 写入 data/uploads/<id>/
7. 追加 history 记录（field: "files"）
8. 返回更新后的附件列表
```

### 5.6 错误码

| HTTP | `error` | 场景 |
| --- | --- | --- |
| 400 | `bad_request` | 参数缺失、字段值非法 |
| 403 | `invalid_token` | 口令缺失或错误 |
| 404 | `not_found` | 活动或附件不存在 |
| 413 | `too_large` | 单文件超过 20MB |
| 415 | `unsupported_type` | 扩展名不在白名单，或 magic number 不符 |
| 429 | `rate_limited` | 同一口令短时间内提交过于频繁 |

## 6. 前端设计

### 6.1 无构建的前端组织

不使用打包器。三个页面各自一个 HTML，共享 `app.js` 与 `style.css`，通过普通 `<script src>` 引入（不用 ES module，避免本地 `file://` 之外的多余约束）。

`app.js` 导出到全局命名空间 `App`，包含四块：

| 模块 | 职责 |
| --- | --- |
| `App.api` | `fetch` 封装、错误提示 |
| `App.field` | 字段渲染（含"未注明"占位与状态徽章） |
| `App.preview` | 附件预览分发（按扩展名选择渲染方式） |
| `App.markdown` | 极简 Markdown 渲染（约 60 行，支持标题/粗体/列表/链接/代码） |

### 6.2 卡片墙渲染

```
GET /api/activities
  → 按状态过滤（默认排除"已结束""报名已截止"）
  → 按合并规则处理（merged=true 的条目不单独出卡）
  → 渲染卡片：名称 + 状态徽章 + 4–5 个关键字段 + 变更提示 + "我是组织者"入口
```

字段渲染统一走一个占位规则：值为 `null` 或空字符串时显示 **"未注明"**（灰色），不留空。这是产品要求里"缺失必须显式呈现"的落点，集中在一处实现。

### 6.3 附件预览分发

| 扩展名 | 实现 |
| --- | --- |
| `.png .jpg .jpeg .gif .webp` | `<img src="/files/...">`，点击放大 |
| `.pdf` | `<iframe src="/files/...">` —— **用 Edge 内置 PDF 阅读器**，无需 PDF.js |
| `.txt` | `fetch` → `arrayBuffer` → 编码探测 → `<pre>` |
| `.md` | 同上取文本 → `App.markdown` 渲染 |
| `.docx` | `fetch` → `arrayBuffer` → `mammoth.convertToHtml({arrayBuffer})` → 注入容器 |
| `.pptx` | **不渲染**。显示提示"PPT 无法在线预览，建议上传方同时提供 PDF 版本" + 下载按钮 |

### 6.4 编辑页交互

```
/edit.html?id=01&token=xxx
  → GET /api/activities/01/verify?token=xxx
      ├─ 有效 → 渲染表单，回填当前值
      └─ 无效 → 显示"口令无效或已失效"，不显示任何可编辑内容
  → 提交：PUT /api/activities/01?token=xxx （JSON）
  → 上传：POST /api/activities/01/files?token=xxx （multipart）
```

表单只呈现**可补充的字段**，每个字段旁标注当前值。留空表示"不修改"（而非"清空"）——用 `null` 与 `undefined` 区分：未出现的键不修改，显式传 `null` 才清空。

## 7. 关键算法与实现细节

### 7.1 中文编码探测（txt/md）

先按 UTF-8 严格模式解码，失败则判定为 GBK：

```js
function decodeText(buf) {
  try {
    return { enc: 'utf-8', text: new TextDecoder('utf-8', { fatal: true }).decode(buf) };
  } catch {
    return { enc: 'gbk', text: new TextDecoder('gbk').decode(buf) };
  }
}
```

**已实测**：GBK 字节（`C4 E3 BA C3 A3 AC CA C0 BD E7`）被 UTF-8 严格模式拒绝并回退 GBK，正确得到"你好，世界"；合法 UTF-8 与纯 ASCII 均正常判定为 utf-8。

### 7.2 文件类型校验（magic number）

仅校验扩展名不足以防改扩展名上传，因此必须读文件头：

| 格式 | 魔数（hex） | 长度 |
| --- | --- | --- |
| PNG | `89504E470D0A1A0A` | 8 |
| JPEG | `FFD8FF` | 3 |
| GIF | `47494638`（"GIF8"） | 4 |
| WEBP | `52494646` + 偏移 8 处 `57454250` | 12 |
| PDF | `25504446`（"%PDF"） | 4 |
| DOCX / PPTX / XLSX | `504B0304`（ZIP） | 4 |
| TXT / MD | 无魔数 | 用"不含 NUL 字节 且 可解码为文本"判定 |

**已知局限（需明确接受）**：docx 与 pptx 同属 ZIP 容器，魔数完全相同，无法仅凭文件头区分，只能依赖扩展名。若上传者把 pptx 改名成 .docx，mammoth 会解析失败——前端需捕获该异常并降级为"无法预览，请下载"。同理，`.doc`（旧二进制格式）不在白名单内，直接拒绝。

白名单：`.png .jpg .jpeg .gif .webp .pdf .txt .md .docx .pptx`。单文件上限 20MB，单活动上限 10 个附件。

### 7.3 时效状态计算

状态**不落库**，每次请求按当前时间实时计算（避免数据过期）：

| 状态 | 判定 |
| --- | --- |
| `已结束` | 有 `schedule` 且可解析出结束时间，且早于当前时间 |
| `报名已截止` | `deadline_status = 明确` 且 `deadline` 已过 |
| `长期` | `deadline_status = 长期` |
| `无需报名` | `deadline_status = 无需报名` |
| `地点待定` | `location_status = 待确认` |
| `报名中` | 其余 |

**实现约定**：数据源中的日期**没有年份**（如"9月24日 22:00"）。方案是在 `data/activities.json` 顶层记录 `term: "2026 秋季学期"`，解析时按该学年补全年份；跨年（如 10 月之后出现的 1 月日期）按"下一年的 1 月"处理。无法解析的日期一律视为"未知"，状态回落到 `报名中` 并在卡片上标注"时间未注明"，**不猜测**。

### 7.4 活动合并（09/20 → 01/03）

种子数据中 `merged: true` 的条目（09、20）是补充通知，规则：

1. 卡片墙**跳过** `merged: true` 的条目；
2. 其 `changes` 数组作为父活动（`parentId`）的初始 `history` 记录导入，使详情页能展示"时间与地点已变更"；
3. 详情页的字段值以父活动为准，变更记录里保留改动前后对比。

## 12. 安全边界与取舍

本系统的安全模型建立在**"只在本机回环地址运行"**这一前提上，以下取舍需明确知晓：

| 项目 | 现状 | 风险与前提 |
| --- | --- | --- |
| 网络暴露 | `listen(3000, '127.0.0.1')` | 仅本机可访问。**若要给他人访问，必须先加访问控制**，不可直接改成 `0.0.0.0` |
| 认证 | 无账号体系，补充口令即凭证 | 96 bit 随机口令不可爆破；但口令经 URL 传递，会被浏览器历史记录。适合内网/演示场景 |
| 上传文件 | 扩展名白名单 + magic number + 大小上限 | **不做病毒扫描**（ClamAV 签名库过重）。仅接收白名单内格式，且不执行任何上传内容 |
| 路径穿越 | 静态与附件路由均做前缀校验 | 见 5.3 |
| XSS | 前端渲染用户文本时统一用 `textContent`，不用 `innerHTML` | 唯一例外是 mammoth 与 Markdown 渲染的 HTML 输出——**需评估**：mammoth 的输出可能含图片引用与外链，Markdown 渲染需禁用内联 HTML |
| 数据完整性 | 原子写 + 变更留痕 | 误改可追溯；无备份机制，建议定期复制 `data/` 目录 |
| 依赖风险 | 零 npm 依赖 | 无供应链风险；但 `public/vendor/mammoth.browser.min.js` 需一次性下载并**固定版本**，纳入版本控制 |

**上传内容的安全处理原则**：系统只存储与预览，绝不执行、不解析为代码、不在服务端渲染。docx 的解析发生在**浏览器端**（mammoth），即使文件被构造为恶意内容，影响范围限于该用户的浏览器会话。

## 15. 实现说明与方案差异

本节记录**实现与本文档前面章节不一致的地方**，以及原因。实现已完成，81 项测试通过。

### 15.1 docx / pptx 预览：改为自研，不用 mammoth

| 项目 | 原方案（§3、§5） | 实际实现 |
| --- | --- | --- |
| docx | 引入 `public/vendor/mammoth.browser.min.js` | **`public/ooxml.js` 自行解压 ZIP 并提取 `word/document.xml` 文字** |
| pptx | 不渲染，提示上传 PDF | **同样提取文字，按页输出** |

**原因**：构建环境无法联网获取 mammoth（`npm pack` 失败）。而这恰好暴露了原方案的一个矛盾——它一边要求"零依赖、可离线"，一边依赖一个需要预先下载的数百 KB 第三方库（体积未实测，因未能下载）。

**实现方式**：docx/pptx 本质是 ZIP + XML，浏览器与 Node 都内置 `DecompressionStream('deflate-raw')`。`ooxml.js` 自己解析中央目录、解压条目、抽取文本，约 200 行，零依赖、离线可用，且**同一份代码可在浏览器与 Node 中运行**，因此能被 `decode.test.js` 用合成 ZIP 直接测试。

**取舍（已接受）**：只提取文字，**不保留版式**（字体、颜色、表格边框会丢失）。对"判断这个活动值不值得去"这个目标，文字内容已足够；需要看版式的场景由"下载原件"覆盖。界面会明确提示这一点。

### 15.2 其他实现细节

| 项目 | 说明 |
| --- | --- |
| `Request.formData()` | multipart 解析使用 Node 内置能力，**没有手写解析器**（§1.3 已实测确认可用） |
| 上传请求体前置保护 | 除单文件 20MB 限制外，另加 `content-length > 64MB` 直接拒绝，避免超大请求先被读进内存 |
| 状态码映射 | 上传失败按错误类型返回 400/413/415（实现初期这里曾把所有错误都映射成 415，被 `upload.test.js` 发现并修正） |
| 合并条目处理 | 09、20 不单独成卡；其 `changes` 写入父活动变更记录，并把地点回填给 01；同时过滤 `to: "不变"` 的空操作记录 |
| 时效状态 | 每次请求实时计算，不落库；日期按学期年份补全，无法解析时不做猜测 |
| `editToken` 保护 | 接口层用 `publicView()` 显式剔除，并有遍历式测试断言 |
| Markdown 渲染 | 先整体转义再套规则，因此**内联 HTML 不生效**；链接仅放行 http/https |
| XSS 测试 | 原方案（§12）把"mammoth 输出可能的 XSS"列为待评估项；改为自研提取后风险大幅降低，仍保留 `frontend.test.js` 覆盖转义与链接协议 |

### 15.3 仍未解决的问题

1. **`pptx` 的版式**：文字可看，图形与排版看不到（见 15.1 取舍）。
2. **docx 与 pptx 魔数相同**（§7.2）：改扩展名后解析会失败，界面降级为"下载查看"，不影响安全。
3. **`data/` 无自动备份**（§14）：误改可凭 `history.json` 追溯，但仍建议手动备份该目录。
4. **补充口令经 URL 传递**（§12）：会留在浏览器历史记录里。仅适用于本机/内网场景。

## 16. 离线单文件版

### 16.1 为什么要做，以及它做不到什么

需求是"能否有一个 HTML 文件直接启动网站"。**浏览器不允许网页启动本地服务**，所以这不是实现问题，而是安全模型决定的边界。可选的形态只有一种：把数据与代码全部内联，整站变成纯客户端应用。

查询证实了两条硬约束，它们直接决定了设计：

| 约束 | 后果 |
| --- | --- |
| `file://` 页面**不能用 `fetch` 读本地文件**（[CORS request not HTTP](https://mdn.org.cn/en-US/docs/Web/HTTP/Guides/CORS%20Errors/CORSRequestNotHttp)） | 数据不能放在旁边的 JSON 里，必须内联 |
| `file://` 下**浏览器存储行为不一致**（[localStorage for local files](https://stackoverflow.com/questions/78146699/accessing-localstorage-for-local-files-from-chrome-and-firefox)） | **不依赖 localStorage / IndexedDB**，改用"导出新文件"持久化 |

**因此离线版的能力边界是**：浏览、筛选、搜索、附件预览、字段补充、导出——全部可用；但**没有口令、没有多人共享**，任何拿到文件的人都能改。需要协作时用服务版。

### 16.2 实现方式：生成，而不是另写一份

离线版是**由源码生成的产物**，不是手写的第二份实现：

```bash
node tools/build-standalone.js          # 生成 校园活动与机会平台.html（约 78KB）
node tools/build-standalone.js --check  # 只校验产物是否为最新
```

`tools/build-standalone.js` 把 `style.css` + `model.js` + `ooxml.js` + `app.js` + `offline.js`
与由种子数据算出的状态**内联**进一个 HTML。为此专门做了一次重构：

- 领域逻辑（状态计算、日期解析、合并回填、字段应用）从 `server.js` 抽到 **`public/model.js`**
- `server.js` 改为 require 该模块（851 行 → 634 行），行为不变（重构后 81 项测试全绿）
- 离线版复用同一份模块 —— **渲染、编码探测、docx 提取、状态判定都只有一份实现**

### 16.3 数据与导出

- 数据放在 `<script id="dsh-data" type="application/json">` 中，页面直接读取，不发任何请求
- 每次补充后 `offline.js` 会把当前状态**同步回该数据块**，因此导出永远是最新的
- 导出用 `<!DOCTYPE html>` + `document.documentElement.outerHTML`：得到一个新的、完整的单文件 HTML，**替换旧文件即可**。不需要任何存储 API
- 写入数据块时把 `<` 转义为 `\u003c`，杜绝数据中出现 `</script>` 截断文档

### 16.4 实现中踩到的两个真问题

| 问题 | 后果 | 处理 |
| --- | --- | --- |
| `offline.js` 的注释里写了 `</script>` | 内联时会**提前截断文档**，页面直接损坏 | 生成器统一把 `<\/script` 转义（`safeScript`）；并有测试断言产物恒为 5 个 script 块且各自语法合法 |
| `generatedAt` 取"当前时间" | 产物**不可复现**：每次生成都不同，"产物是否为最新"的校验永远失败，提交也产生无意义 diff | 改为使用种子数据的基准时间，产物只由源码决定 |

### 16.5 验证方式

离线版是自包含的，无法靠"页面能打开"来验证，因此 `test/standalone.test.js`（13 项）覆盖：

1. **产物是否为最新**（源码改动后忘记重新生成会直接失败）
2. **完全自包含**：零外部 `src`/`href`、无外部样式表、无外部脚本
3. **每个内联 script 块语法合法**，且恰好 5 块（防止 `</script>` 截断）
4. **内嵌数据与服务版由种子数据算出的结果逐字节一致**
5. **不内嵌任何口令**（离线版不应有 `editToken`）
6. **模拟导出**后结构仍然完好、改动被保留
7. **在最小 DOM 桩中真实执行产物**：按产物内顺序跑四个脚本，确认启动不抛错，并渲染出 22 张卡片、显示回填的地点与"未注明"占位

第 7 项是这里最有价值的检查——它能在没有浏览器的环境下抓到"启动即抛错导致页面停在加载中"这类问题，而语法检查抓不到。

### 16.6 两种版本的取舍

| | 离线单文件版 | 服务版 |
| --- | --- | --- |
